# Architecture

## Project overview

This is a React-based portfolio site deployed to Cloudflare Pages. The site is a static single-page application (SPA) with GitHub repository data fetched and baked into the build at deploy time.

## Directory structure

```
├── client/              # Frontend React application (the main SPA)
│   ├── src/
│   │   ├── components/  # Reusable React components (UI kit)
│   │   ├── pages/       # Page-level components rendered by the router
│   │   ├── lib/         # Utilities: GitHub API integration, social links, cn() helper
│   │   ├── hooks/       # Custom React hooks
│   │   ├── types/       # TypeScript type definitions
│   │   ├── App.tsx      # Root app component and client router
│   │   ├── main.tsx     # Entry point
│   │   └── index.css    # Global styles (Tailwind directives)
│   └── public/          # Static assets (favicon, fonts, robots.txt)
├── shared/              # Shared schemas and configuration
│   ├── featured-repos.ts   # List of repos to show and their star/fork counts
│   ├── fleet.ts            # Infrastructure/deployment info model
│   ├── fleet.test.ts       # Tests for fleet parsing
│   ├── infra.ts            # Infrastructure schema definitions
│   ├── infra.test.ts       # Tests for infra schema
│   └── schema.ts           # Shared TypeScript types
├── server/              # Development server stub (not used in production)
├── worker/              # Cloudflare Workers edge scripts
├── dist/                # Production build output (gitignored)
├── attached_assets/     # Source images and assets
└── Configuration files
    ├── vite.config.ts       # Build configuration and GitHub stats fetching
    ├── tailwind.config.ts   # Tailwind CSS theme configuration
    ├── tsconfig.json        # TypeScript configuration
    ├── vitest.config.ts     # Test runner configuration
    └── wrangler.jsonc       # Cloudflare Workers configuration
```

## Data flow

### Build time

1. **GitHub stats fetching** (`vite.config.ts`)
   - During `npm run build`, Vite runs `fetchRepoStats()`
   - Fetches star/fork counts from GitHub API for all repos in `featured-repos.ts`
   - Bakes the stats as a global variable `__GITHUB_STATS__` into the production bundle
   - Falls back gracefully if GitHub is unreachable (returns empty stats)

2. **Vite build**
   - Compiles React + TypeScript → JavaScript
   - Bundles with Tailwind CSS (via `tailwind.config.ts`)
   - Outputs to `dist/public/` as a static SPA

### Runtime

1. **Client loads**
   - Browser requests `index.html` from Cloudflare Pages
   - SPA shell renders; client-side router handles navigation

2. **GitHub stats display**
   - `client/src/lib/github-api.ts` reads pre-baked `__GITHUB_STATS__`
   - Components call `getRepoStats()` to display star/fork counts
   - No runtime API calls to GitHub (all data is client-side)

3. **Deployment**
   - `wrangler.jsonc` configures Cloudflare Pages hosting
   - `_redirects` file handles SPA client-side routing (all unknown paths → `index.html`)
   - `404.html` fallback is generated by the build for client-side 404 handling

## Key design decisions

### Baked stats, not live fetches
- **Why:** Cloudflare Pages is a static host; no backend needed. Fetching at build time eliminates runtime dependencies and CORS issues.
- **Trade-off:** Stats are stale until the next deploy. Redeployment frequency controls freshness.

### Path aliases
- `@` → `client/src/` — import from `@/components/...`
- `@shared` → `shared/` — import from `@shared/featured-repos`
- `@assets` → `attached_assets/` — static images and media
- **Why:** Reduces relative path noise (`../../../`) and makes import paths more stable across refactors.

### TypeScript strict mode
- `tsconfig.json` enforces strict type checking
- All React components are fully typed
- Shared schemas are exported as TypeScript interfaces for cross-layer type safety

### Test-driven development
- Unit tests in `*.test.ts` files alongside source (e.g., `fleet.test.ts` tests `fleet.ts`)
- Run with `npm run test` (once) or `npm run test:watch` (continuous)
- UI tests are manual; automate regression journeys if coverage expands

## Deployment

### Environment variables

No runtime secrets are needed (all data is static/public).

### Build and deploy

**Manual (for testing):**
```bash
npm run build
npm run preview  # Preview the built site locally
```

**Automatic via Cloudflare Pages:**
- Connect the repository in Cloudflare dashboard
- Build command: `npm run build`
- Build output directory: `dist`
- Root directory: `/` (empty)

Commits to `main` trigger automatic builds and deploy.

### SPA routing

`_redirects` file tells Cloudflare Pages to serve `index.html` for all 404s, enabling client-side routing. The React Router handles all page transitions client-side.

## Development workflow

1. Start dev server: `npm run dev` (runs Vite with HMR)
2. Make changes; browser auto-refreshes
3. Write tests alongside code
4. Run `npm run check` to validate TypeScript
5. Commit and push; CI runs tests
6. Once merged, Cloudflare Pages auto-deploys

## Adding features

- **New page:** Add component to `client/src/pages/`, update router in `App.tsx`
- **New shared data:** Add to `shared/` and export types
- **New component:** Add to `client/src/components/`, export from index file if reusable
- **New GitHub repos to track:** Update `shared/featured-repos.ts` and redeploy

## Future considerations

- If dynamic data is needed (e.g., live blog feed), introduce a serverless backend or edge function
- If GitHub stats need to refresh without full redeploy, consider a scheduled worker to update a KV store
- If analytics or user interaction tracking is needed, integrate a tracking service (e.g., Plausible, already privacy-focused)
